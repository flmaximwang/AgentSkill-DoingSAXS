# 重跑流水线整批结果并核对产物

## When to Use

用户说「把 <数据目录> 里的结果都重跑一遍」时（刚改过流水线脚本、刚装好新依赖、或数据里加了新样品）。同类问法：「都重跑一遍」「加了新样品重跑」「哪个样品/哪个节点失败了」。


**边界**：不负责流水线本身的参数选择（转对应 `run-a-*-pipeline-end-to-end` skill），不负责 skill 的安装/更新（转 maintain-hermes-skills）。

这类流水线一般是：一个已安装的 skill 带几个脚本（逐样品跑 + 汇总 + 出图），产物落在与数据平行的 `processed/<模式>/` 下。**脚本由别人维护，只调用 + 核对**；发现脚本缺陷报给用户，不要顺手改。

## 重跑前先核两件事（都真踩过）

1. **投递有没有被换过**——逐样品核**四件套**并与上一轮记录对比：帧数、监视器（`.Iochamber`）、采集日志（`.log`）、逐帧 header txt。
   **帧数变多、或监视器/日志从无到有 = 数据被补全或重新下机**：上一轮据此写下的质量判定**全部作废**，尤其「这条数据不可用」——本次就是这么翻案的（445 帧无监视器 → 以为色谱是阶跃、判不可用；换成完整 1500 帧 + 监视器后峰清晰可见，同一条流水线正常出结果）。
   作废要落到文件：删掉/改写旧的结论文件（`结果不可用-README.md` 之类），并在汇报里点名「哪条判定作废、新结论是什么」，否则旧结论会被后来的人当现状引用。
   （同理：txt 被清空或换了来源，归一化那一支要重跑而不是沿用因子表。）
2. **跑的是不是更新后的那套脚本**——用户说「我更新了 skill」之后，skill 可能**搬了家、改了名**（本次 SEC 流水线从 `AgentSkill-UsingBioXTASRAW` 搬到 `AgentSkill-DoingSAXS`，profile 里换成 hub 安装副本）。
   先确认版本：读 `~/.hermes/skills/.hub/lock.json` 的 `installed[<name>].identifier` 看来源仓库，再决定要不要 `hermes skills update <name>`（该子命令**没有 `-y`**，只有 `--force`）。
   `update` 回一句「you have local edits (update would overwrite them)」**不等于副本真被手改过**：副本落后于仓库、或 lock 里的 `source_revision` 比盘上内容旧，都会得到这句。放行 `--force` 前先逐字节比：`diff -rq <仓库 clone>/skills/<skill> ~/.hermes/skills/<类目>/<skill>`，差异要能**全部解释成仓库侧的提交**；只存在于安装副本里的内容（有人直接手改了 profile 副本）会随 `--force` 静默消失，有这类差异就先把它回移植进仓库再 force。
   更新完回读两样：`diff -rq` 只剩 `__pycache__`、lock 的 `source_revision` == 仓库 HEAD——不核对就等于没更新。
   改脚本要改**仓库 clone**（source of truth）再 commit→push→update，别直接改 profile 里的副本；安装/更新机制本身转 `maintain-hermes-skills`。

## 步骤

1. **重跑范围 = 数据目录里的全部样品**，不是「已有结果的样品」。先列两遍：数据目录的样品目录、结果目录的样品目录，分三类处理——有数据没结果（补跑）、有结果没数据（问用户留删）、两边都有（重跑）。数样品用代码数（`os.listdir` 过滤），别用眼睛数。
2. **旧结果先移不先删**：`mkdir -p <结果根>/_prev_<YYYYMMDD>`，把每个样品目录 `mv` 进去，移完核对文件数（移前 = 移后）。重跑必须可回退；删文件要用户点头。
3. **结果树里可能有别人的产物**。出现你没创建过的目录（另一个并发会话、用户自己跑出来的）先查身份——mtime、内容、里面 README 写的生成者——再决定是否覆盖；覆盖了就在汇报里**点名**换掉了谁的东西。
4. **先用 1 个样品探针**（新版本脚本、新装的依赖都可能有坑），确认整条链能通、拿到每样品耗时，再放整批。整批写成一个 driver：`ThreadPoolExecutor(max_workers=3)`，每样品一个 `subprocess.run([...], stdout=日志文件)`。**别用 `xargs -P` 内联长命令**，命令行拼装长度会直接失败。
5. **exit 0 ≠ 成功——这条最容易漏。** 流水线内部节点失败（积分/扣减/IFT/3D 重建/README 生成）多数只写进日志，退出码仍是 0。跑完必须逐日志 grep 失败标记（`failed|失败|not written|Traceback`），把「失败样品 + 失败节点 + 原始报错行」列进汇报。
6. **收尾脚本是独立一步，必须显式再跑**：逐样品之后，汇总表 / 总览图 / 根 README 各自是单独脚本（顺序：逐样品 → summarize → plot）。跑完做完整性核对：每个样品目录该有的节点目录与 README 是否齐——**缺了就是生成器崩了**，去日志找 traceback，别当「它本来就不写」。
   补跑单个样品之后同样要再跑一遍汇总与总览：汇总停在上一次的盘面时，样品数与每个数字都跟盘上对不上，而你不会立刻发现。
7. **传参照文档，不照默认值**：脚本 argparse 的默认落点常与 SKILL.md 约定的落点不一致（默认写进样品目录，文档要求写同级 `_embed/<样品>/` 之类）。按文档显式传 `--out-dir`，并在汇报里点出这个不一致——下一个人照默认跑，产物就会落在下次重跑会被清掉的位置。
8. **验收看产物本身**：图用眼睛看（vision 核模型/曲线确实落在应有的范围里），关键数字与日志/JSON 对得上，汇总脚本的自动分类与逐样品 README 的结论不矛盾。数字和上次不一致时，先定位到「哪个输入/哪个口径变了」再报，别把差异归给「版本不同」了事。

## 重生丢失的产物（自己的仓库）：改原驱动程序，不另起旁路脚本

**适用**：产物丢了要重生、或原流程要改，而代码在**用户自己的仓库**里（典型：`<仓>` 的 `pipelines/<版>/…`）。
这时**改仓里那份原代码**；不要写一个平行的 `redo-*.py` 侧脚本 —— 用户会明确要求
「我们修一下原来的代码再跑」。侧脚本与主流程分叉，下一次维护时没人知道该跑哪个。
（若是安装副本 / 别人维护的脚本，仍按上面「重跑前先核两件事」处理。）

改原驱动**四处必查**（改完 `py_compile` / 从 notebook 格里抽源码 `compile()` 各跑一遍）：

1. **删掉开场「重跑先清目录」**：典型是 `if design_dir.exists(): shutil.rmtree(design_dir)`。
   补跑时目录里往往还活着别的产物（日志、序列清单、参数记录），照原样跑会把**幸存文件删掉**。
2. **完成判据从「标志文件存在」换成「按产物清单逐文件判缺」**：原驱动常写
   `glob("*<最后一个产物>")` 判「已完成」——而缺口里多数目录只缺 1–2 个文件 ⇒ 会**整批漏跑**。
   把「一次运行会产出的所有文件」列成常量，`missing = [n for n in EXPECTED if not (d/n).exists()]`，空则 Skip。
3. **改重跑安全的动作**：`ln -s`→`ln -sf`、`cp`→`cp -n`、`> log.txt`→`>> log.txt`（或先追加一行分隔注释）。
   否则第二次跑报 `File exists` 或覆盖掉原始日志。
4. **要跑哪棵树 / 程序在哪 / 参数文件在哪 / 并发几核，都改成环境变量**（`OUTPUT_DIR` `APP_DIR` `RESFILE` `CPU_CORES`）：
   一份驱动同时服务多条树；写死在代码里的路径迟早过时。

跑之前 `--dry-run` 打印「待跑 N / 跳过 M」，先看数再放全量。**每个样品目录自带的输入文件就是输入**
（如 `<样品名>.pdb`）——别再去外部找输入树。清单（哪些目录缺哪些文件）单独出一份 TSV，
驱动与清单对齐后再跑。

交付：原文件备份到批次目录、给出 `git diff --stat` 与关键 diff、说明「未提交」并让用户决定是否提交 ——
**不要自作主张 commit 他的数据仓**；他明确说「并提交」时才提交（提交后 `git status` 要干净，`git show --stat` 里不能混进 `__pycache__` 之类）。

### notebook → 步骤脚本（.ipynb → .py）

用户要把流水线的 notebook 全部转成脚本、让每一步由 `main.sh` 指挥时：

- **`%%writefile <path>` 格 = 嵌在 notebook 里的另一个文件**：转 py 时必须把那格内容真的写成 `<path>`
  实体文件，py 里留一行注释指过去；照搬成 `get_ipython().run_cell_magic(...)` 的脚本离开 IPython 跑不了。
- **同目录多个 notebook 要写同一个 `run.py`**（3.1 与 3.2 的典型）：落盘产物加 notebook 前缀
  （`<notebook-stem>__run.py`），**绝不覆盖已存在的同名文件** —— 先转的那份会被后转的静默吃掉。
- **改过的模块副本会被 notebook 里的旧副本盖掉**：驱动 `from scripts.<mod> import …`，而某格把该模块的
  **旧版**写进 `scripts/` ⇒ 补丁无声失效（`rmtree` 又回来了）。转完把打过补丁的那一份同步到被 import
  的路径，并 grep 关键改动确认在位。
- **校验用最新的 python**：`py_compile` 的假失败多来自语法版本（f-string 需 ≥3.12），别当代码坏了；
  同时分清「本次转换引入」与「原有」错误（`git log -1 -- <file>` 看上次谁动的）。
- py_compile 会在树里生成 `__pycache__`/`*.pyc` → 先加 `.gitignore` 再提交；原 notebook 备份一份到批次
  目录再删。
- 入口与环境：`main.sh <step> [env]` + `envs/<名>.sh`；**环境名与解释器路径向用户要，不要猜**，
  「跑起来才报 `No module named <内部包>`」是环境不匹配，不是代码缺陷。

### 交付口径：按 Step 列归属表

用户会逐字追问「每个步骤到底生成哪些文件」。交付时按**流水线 Step 顺序**给一张表，每行：
`Step（目录 / notebook）· 输入 · 产出（逐个文件名，不写「等若干」）· 判据与依赖`；
再单列一段「**不属于任何一步**」的输入（参数文件、上游起点 pdb）—— 用户最容易把**输入**当成丢掉的
产物，把「输入 vs 产物」分开列能一次消掉这个误解。叙述顺序也按 Step 走（每类数据先点 Step）。

### 把老脚本 port 到新包 / 换成新版第三方程序

旧包（`modules/`、被改名搬家的库）换新包，或老程序换新版本时，四处必查：

1. **区间参数的语义**：老代码写 `helices=[(1, 25)]` 是**闭区间**。搬进新 helper 时若写成
   `np.isin(res_id, list(spec))`，tuple 就变成 `[1, 25]` 两个残基——**不报错**，mask 只命中 1–2 个残基，
   几何全错，直到下游某步才炸（或干脆不炸，静默产出垃圾坐标）。区间一律归一化成 `range(a, b+1)`，
   并给每个 mask 加一句「命中的残基数是否落在合理区间」的断言，让这种错误当场出声。
2. **完成判据要跟着程序版本走**：新版本常改产物名（老 `<旧名>beststruct0001.pdb` → 新 `<resfile 名截断>_mod0001.pdb`），
   按老名单逐文件判缺的驱动会把**已跑完的整批当没跑**、反复重跑。落地前先问程序自己（`./<bin> --command=<cmd> -h`）
   **并跑一个样品看实际落哪些文件**，再按实际产物 glob 判齐；老名单留作历史注释。
3. **命令行旗标也要跟版本对**：仓库里更晚的流水线（`<仓>/pipelines/<更高版本>/`）通常已经在用与当前程序匹配的旗标。
   把「原版驱动怎么写 / 后续版本怎么写 / 当前二进制 `-h` 怎么写」三份命令行列出来交给用户拍——
   自己替他选旗标会改设计语义，那是有科学后果的决定，不是跑不跑得起来的问题。
4. **静态符号核对 ≠ 语义核对**：用 AST 扫新包确认 import 名/方法名都在，只能抓「名字写错、包改名、模块搬位置」，
   抓不到「参数语义用错」。语义靠真跑一个样品 + 与旧结果对表。

**最强的结构核验 = 与幸存的原件比对文件名集合**：重生一棵树后，若原始树还在（别的源、备份、归档），
把两边文件名 `sort` 后 `comm -12/-13/-23` 对一遍，报「相同 / 只我有 / 只原始有」三个数。
只比数量（2001 vs 2001）给不出这个保证；逐名相同才证明 seed + 参数 + 命名全对。
（把重生树的比对结果写进 plan 的块 note，比写在聊天里活得久。）

## 坑（都真踩过）

- **`sorted()` 套住拼接的候选表会毁掉优先级**：`sorted(glob(优先组) + glob(次选组))` 让次选组插到前面，静默选中错误的候选文件。偏好的候选顺序要**先各自排序再拼接**，或显式指定。换候选文件常常只差 0.2 的分数，但口径全变了——报数字时必须写明用的是哪个文件。
- **入参形态不对的脚本会静默空转**：要目录的脚本给成文件路径时不报错、退出码 0、什么都不写。跑完查输出文件的 mtime/内容，不要只看退出码（与第 5 条同源：退出码不是证据）。
- **README/汇总不会自动刷新**：重跑后旧 README 留在原位冒充新结果。核对它的 mtime 和里面的数字是否来自本次运行；必要时重跑生成器。
- **嵌套取值只在最外层加 `isinstance` 守卫不够**：`(x or {}).get(k)` 挡不住「x 是非空**字符串**」——非空字符串为真，`or {}` 不生效，`.get` 当场 `AttributeError`。上游把「这一步失败/跳过」写成字符串状态塞进同一个字段（成功时才是 dict）时，报告生成器就只在那一个样品上崩，日志里只留一行 `WARNING: …not written`，该样品静默缺 README。守卫要落到每一层：`_v = d.get(k) if isinstance(d, dict) else None`、`(_v if isinstance(_v, dict) else {})`；并用「逐样品产物/README 齐不齐」兜底。
- **别在整批还在跑时再并发起同一批**：CPU 争抢让两边都变慢；探针先跑正是为了避免「跑了 20 分钟才发现参数不对」。
- **上下游的"文件名契约"不核对，下游会静默少做一半**：上游流水线写 `models/<前缀>_denss.mrc`，下游 embed skill 只找 `models/denss.mrc`/`denss_current.mrc` → 它把该分支判成"没有电子云"，不报错、不退出非 0，只少出产物（图里少一张、分数少一半）。
  接上下游之前先读下游的"发现输入文件"那段代码，把它认的名字与上游实际产物的名字逐个对；不一致就改**发现方**（认两套命名，并排除 `_support` 这类中间文件），按仓库约定 commit→push→update，再回读确认新代码在位。改不动上游时，也别拿"手动改个文件名/软链"顶替——那是无 lock 的手拷产物，把不一致显式写进汇报。
- **序列开头的全零帧不是坏数据**：快门未开时整幅图为零 → `I(q) ≡ 0` 的曲线（可占开头十几到几十帧）。判据：数前几帧的非有限/负/零点数。处理：buffer/sample 区间避开它们（区间给在第一个正常帧之后），series 图前面那段平零不必解释成漂移；不要把零帧算进 buffer 平均。
- **同一批任务反复重启后，旧运行的完成通知会陆续到达，并冒充新失败**：长批次改参数重跑时，早先那次（缺输入 / 缺依赖）的退出通知常在几十分钟后才送达，退出码 1、输出为空——看着像刚崩的那一次。先拿通知里的 session/pid 与**当前在跑的那次**对照再决定动不动；不要照着通知里那条命令去「复现修复」（它可能早就修好并跑完了）。「这批到底成没成」一律看盘上的产物与打包件，不看通知。
- **批次产物先打包再清散件，一次删除要一次批准**：一棵树上万小文件时，先打成 `tar.zst` + 落一份 `pack-manifest.json`（每棵树：文件数、包大小、包内成员数），核验「包内文件数 == 盘上文件数」之后才清散件。删除会触发审批；用户不在（睡觉）时审批超时 = **未获批** —— 停手、把它记进 plan 等回复，别换个写法重试。
- **旁支目录不是样品**：`_prev_*`、`_logs`、`_summary`、`_embed` 与样品目录同级，汇总脚本只认样品目录；自己遍历时也要排除，否则汇总数会多出来。

## 汇报（用户口径）

结论先行、分点、每个数字具体（NSD/correlation/Rg 之类带上单位与口径），失败项与未定论项**分开**写，产物落点给绝对路径，最后列出「等你拍板」的少数几个决定（要不要删冗余副本、要不要修脚本、要不要提交/安装）。别把「一次跑完的中间过程」当汇报主体。
